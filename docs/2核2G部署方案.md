# 2核2G 精简部署方案（壹页简历 + Supabase）

> 适用：腾讯云/阿里云轻量 **2核2G · 3M带宽 · 40G 云盘**
> 目标：壹页简历 + 精简 Supabase，稳定跑通商业化 MVP
> 关联：[国内轻量服务器部署.md](./国内轻量服务器部署.md)（完整流程在此之上简化）

---

## 一、这套配置能干什么、不能干什么

| ✅ 能 | ❌ 不能 |
|---|---|
| 壹页简历完整功能（建简历/AI翻译/导出） | 拼团平台（秒杀流量，内存顶不住） |
| 注册/登录/订单/会员（Supabase 精简版） | 未来数据量巨大时的性能优化 |
| mock 支付 + 备案后切微信支付 | 高并发（>30 并发明显卡顿） |
| 商业化 MVP：撑到月营收 1-2 万 | 需要大数据分析/实时消息 |

**预期负载**：日 UV <2000，月付费用户 <300，完全够用。

## 二、快速开始（按顺序执行）

### 1. 服务器初始化 + Docker 安装

按《国内轻量服务器部署.md》第 2~3 章操作（Docker 国内镜像加速必做），然后：

### 2. 配置 swap（2G 内存的兜底，必做）

```bash
# 把 deploy/2g/setup-swap.sh 上传到服务器，然后：
sudo bash setup-swap.sh
```

> 2G 内存 + 2G swap = 高峰期 Postgres 有缓冲，避免 OOM 杀进程。

### 3. 部署 Supabase（精简版）

```bash
cd /opt
git clone --depth 1 https://github.com/supabase/supabase.git
cd /opt/supabase/docker
cp .env.example .env
# ← 编辑 .env，填写 §4 生成的密钥（POSTGRES_PASSWORD/JWT_SECRET/ANON_KEY/SERVICE_ROLE_KEY）

# 用 2G 精简版替换官方 docker-compose.yml：
mv docker-compose.yml docker-compose.orig.yml
cp <你上传的>/deploy/2g/docker-compose.2g.yml docker-compose.yml

docker compose up -d
docker compose ps        # 应有 4 个服务：api-gw / auth / rest / db，全部 running+healthy
```

> ⚠️ 官方模板依赖 `./volumes/db/*.sql` 迁移文件，克隆后这些文件已在仓库里，**无需额外操作**。
> ⚠️ `.env` 里 `API_GW_HTTP_PORT=8000` 保持不变，`VITE_SUPABASE_URL` 指向 `http://服务器IP:8000`。

### 4. 部署壹页简历

按《国内轻量服务器部署.md》第 6 章：上传项目 → 配 `.env` → `docker compose up -d --build`。

壹页简历 `.env` 关键项（指向自托管）：

```ini
VITE_SUPABASE_URL="http://服务器公网IP:8000"      # 域名就绪后改 https://resume.xnkun.com
VITE_SUPABASE_ANON_KEY="生成的ANON_KEY"
SUPABASE_SERVICE_ROLE_KEY="生成的SERVICE_ROLE_KEY"
PAYMENT_PROVIDER="mock"                          # 备案后改 wechat
APP_URL="http://服务器公网IP:3000"                # 域名就绪后改 https://resume.xnkun.com
```

### 5. 验证

```bash
# Supabase
curl -s http://127.0.0.1:8000/auth/v1/health     # → {"status":"ok"}
# 壹页简历
curl -s http://127.0.0.1:3000/api/health          # → {"status":"ok"}
```

然后浏览器访问 `http://服务器IP:3000`，注册账号 → 建简历 → 模拟支付，完整走一遍。

## 三、2G 内存的专项优化（本方案核心）

### 内存预算

| 组件 | 分配上限 | 实际占用 |
|---|---|---|
| Postgres（shared_buffers=256MB） | 1GB | ~400-600MB |
| Envoy 网关 | 256MB | ~40MB |
| GoTrue (auth) | 192MB | ~40MB |
| PostgREST | 128MB | ~25MB |
| 壹页简历 Node | （独立容器） | ~200-300MB |
| Ubuntu + Docker | — | ~400-600MB |
| **合计** | | **~1.3-1.6G**（swap 兜底） |

### 三个关键优化点

1. **裁掉 8 个不需要的服务**（studio/imgproxy/meta/realtime/storage/functions/supavisor/deno-cache）——官方全套要 4-6G 内存，砍掉后省 70%+。
2. **压 Postgres 参数**：`shared_buffers=256MB`、`work_mem=2MB`、`max_connections=50`——防止高并发时内存爆掉。
3. **swap 兜底**：`setup-swap.sh` 建 2G swap，并调 `vm.swappiness=10`（尽量用内存，逼近满才换页）。

### 为什么保留 Envoy 而不拆掉？

壹页简历前端 SDK（supabase-js）需要统一入口路由 `/rest/v1` 和 `/auth/v1`，Envoy 就是干这个的（占内存极小）。砍掉它省的内存 <50MB，却要多配一层 nginx 手动路由，不值。

## 四、监控与运维（2G 机器要勤看）

```bash
# 内存监控（重点！发现 OOM 前兆：Memory 接近 2G 且 swap 被大量占用）
free -h

# 容器内存占用
docker stats --no-stream

# 看是否有进程被杀
dmesg | grep -i oom | tail
```

**预警信号**：`free -h` 里 swap 长期占用 >1G → 说明内存不够，考虑：
- 升配到 4核8G（预算允许时）
- 或减少容器内存上限，优先保 Postgres

## 五、常见问题

**Q: `docker compose up` 报 `depends_on` 依赖的服务不存在？**
A: 说明没替换干净，`docker-compose.yml` 里仍有 studio 等被删服务的残留。确认已用本目录的 `docker-compose.2g.yml` 整体替换（`mv` 原文件后 `cp` 新的）。

**Q: 8000 端口访问不了 /rest/v1？**
A: 检查 `.env` 的 `API_GW_HTTP_PORT` 是否为 8000，且安全组/防火墙放行 8000、3000 端口。

**Q: Postgres 起不来？**
A: 查看日志：`docker compose logs db | tail`。常见是 `.env` 的 `POSTGRES_PASSWORD` 与 `JWT_SECRET` 未正确填写，或 `./volumes/db/data` 有残留脏数据（`sudo rm -rf volumes/db/data` 后重试）。

**Q: 之后想升级到 4核8G？**
A: 直接换回官方完整 docker-compose（`mv docker-compose.orig.yml docker-compose.yml`）即可，数据卷（`volumes/db/data`）保留，**不丢数据**。
