# 壹页简历 — 邀请奖励功能需求分析文档

> **版本:** v1.1
> **更新日期:** 2026-08-29
> **状态:** 需求分析（未开发）
> **关联系统:** Supabase Auth + Postgres / React 前端 / Node 服务端

---

## 1. 背景与目标

### 1.1 背景

壹页简历已上线会员与单次导出付费体系。非会员用户默认 `remaining_pdf_exports = 0`，导出 PDF 需要购买单次导出（`single_export`）或开通会员。当前获客完全依赖自然流量，缺少用户自传播机制。

### 1.2 目标

通过「老用户邀请新用户注册得免费导出额度」的裂变机制，以近乎零成本拉新：

- **核心指标**：注册转化率提升、新增注册用户数增长
- **间接目标**：新用户注册后拥有 1 次免费导出体验，为后续转化付费会员铺垫
- **预算控制**：单个有效新用户的最大营销成本 = 2 次导出额度（≈ 单次导出单价 × 2，远低于买量成本）

### 1.3 范围

| 项 | 范围内 | 范围外 |
|----|:---:|------|
| 邀请码生成与展示 | ✅ | — |
| 邀请链接 / 手动邀请码识别 | ✅ | — |
| 奖励发放（邀请人 / 新用户） | ✅ | — |
| 反作弊基础防线 | ✅ | — |
| 管理后台查看 / 撤销 | ✅ | — |
| **后台配置开关（活动启停）** | ✅ | — |
| **官网首页活动设计说明** | ✅ | — |
| **users 表 RLS 安全缺口修复** | ✅（随活动开发一并做） | — |
| 活动页 / 落地营销页 | — | 后续可选 |
| 会员用户专属奖励（积分等） | — | 后续可选 |

## 2. 已确认的核心决策

以下决策已在需求澄清阶段确认：

| # | 决策项 | 结论 |
|---|--------|------|
| D1 | 奖励触发条件 | **注册成功即发放**（新用户完成邮箱密码注册即视为有效） |
| D2 | 新用户是否得奖 | **新用户也送 1 次**导出额度 |
| D3 | 邀请识别方式 | **链接带参 + 手动邀请码** 两者都要 |
| D4 | 参与资格 | **所有登录用户**都可参与（含会员），会员不降级为仅非会员 |
| D5 | 活动时效 | **不限时**，作为长期功能存在 |
| D6 | 配置开关 | 后台增加**活动总开关**：开启则规则与相关显示入口生效，关闭则全部隐藏 |
| D7 | 服务协议补充 | **不补充**邀请奖励条款 |
| D8 | 新用户奖励门槛 | **不用邮箱验证**，注册即发 |
| D9 | 官网首页 | 首页**增加活动设计说明板块**（随开关启停） |
| D10 | 安全缺口修复 | users 表 RLS 缺口**随本功能开发一并修复** |

> ⚠️ **风险提示（D1 + D4/D8 组合）**：注册即发、全员可参与、无邮箱验证，意味着无需任何使用行为即可触发奖励，是**最高作弊暴露面**的配置。本方案配套最低限度反作弊防线（见 §7），并在 §10 给出监控与升级建议。若后续发现刷量严重，可通过配置开关停用活动或升级触发条件（改为「完成首次导出」/「完成简历保存」/邮箱验证），无需重构架构。
>
> ⚠️ **风险提示（D7）**：已确认**不补充**服务协议邀请奖励条款。若后续发生奖励争议，因无条款依据，平台对「违规撤销」的处置权说明存在法律模糊地带；建议至少在后台撤销功能上保留完整审计记录（§7 AC-6），以在极端情况下降风险。

## 3. 角色与用户故事

### 3.1 角色

| 角色 | 说明 |
|------|------|
| **邀请人** | 已注册用户，分享自己的邀请链接 / 邀请码 |
| **新用户** | 通过邀请链接或手动输入邀请码完成注册的用户 |
| **管理员** | 通过管理后台查看邀请数据、撤销异常奖励 |

### 3.2 用户故事

- **US-1** 作为已注册用户，我希望在个人中心看到「邀请好友」入口和我的专属邀请码/链接，以便一键分享给好友。
- **US-2** 作为邀请人，我希望看到「已邀请 N 人、已获得 X/2 次免费导出」的进度，以便知道还能获得几次奖励。
- **US-3** 作为被邀请的新用户，我通过好友的链接点进来注册，无需手动填码也能被自动识别。
- **US-4** 作为被邀请的新用户，我也可以选择手动输入好友的邀请码完成注册。
- **US-5** 作为新用户，注册成功后我自己也获得 1 次免费导出额度，用于体验导出功能。
- **US-6** 作为导出额度为 0 的用户，我希望在导出确认弹窗里看到「邀请好友免费获得导出额度」的引导。
- **US-7** 作为管理员，我希望能在后台看到每个用户的邀请码、邀请人数、奖励发放情况，并能撤销异常奖励。
- **US-8** 作为管理员，我希望能在后台通过一个**总开关**随时开启/关闭整个邀请活动；关闭后所有邀请相关显示入口和发放规则立即失效。
- **US-9** 作为访客，我希望在官网首页能看到本次邀请活动的设计说明，清楚了解「邀请好友、双方各得 1 次免费导出」的玩法。
- **US-10** 作为开发者/管理员，我希望邀请活动关闭后，历史已发放的奖励不受影响（不回收）。

## 4. 核心规则

### 4.1 奖励规则

| 规则 | 说明 |
|------|------|
| **R1** | 每个**有效新用户**注册成功，该新用户自己 **+1** 次 PDF 导出额度 |
| **R2** | 每个**有效新用户**注册成功，其邀请人 **+1** 次 PDF 导出额度 |
| **R3** | 邀请人通过邀请获得的奖励**累计封顶 2 次**（`referral_bonus_count ≤ 2`） |
| **R4** | 邀请人数不设上限；邀请人达 2 次上限后，后续新用户仍 +1（R1），但邀请人不再 +1 |
| **R5** | 新用户奖励每人仅 1 次（注册时发放），不存在累计上限问题 |
| **R6** | 奖励额度与购买/其他来源额度**同池累计**（均写入 `remaining_pdf_exports`），不区分来源展示 |
| **R7** | 邀请人**不能邀请自己**（新用户的邀请码不能是自己的邀请码） |
| **R8** | 一个被邀请人只能归属一个邀请人（`referrals.invitee_id` 唯一），重复绑定幂等返回 |
| **R9** | 活动**总开关关闭期间**：所有邀请相关显示入口（个人中心卡片、导出弹窗引导、首页活动说明、注册表单邀请码输入框）**全部隐藏**；发放 RPC 拒绝发放（返回 `activity_closed`） |
| **R10** | 活动总开关**开启/关闭不回收历史已发放奖励**；关闭期间注册的用户事后开启活动也**不补发**（以发放时刻的开关状态为准） |

### 4.2 会员用户参与说明（D4）

- 会员（`tier = member`，额度 999）**也可发起邀请**，奖励照常记录并写入 `remaining_pdf_exports`，但对会员无实际额度意义。
- 会员参与的核心价值是**帮平台拉新**（被邀请人获得 1 次额度，是未来的付费潜在用户）。
- 后续可扩展：会员奖励可改为「邀请荣誉」等其他激励（范围外，不实现）。

### 4.3 活动总开关机制（D6，新增）

**目的**：运营无需发版即可随时启停邀请活动；关闭时用户侧看不到任何活动痕迹，规则同步失效。

**开关形态**：后台「系统设置」新增开关「邀请奖励活动」（布尔值），存入**服务端配置表**（见 §9.5 `app_config`），由管理员操作。

**开关生命周期**：

| 状态 | 规则（R1-R8） | 个人中心/导出弹窗/注册表单/首页活动说明 | 发放 RPC |
|------|:---:|:---:|:---:|
| **开启** | 生效 | 显示 | 正常发放 |
| **关闭** | 不生效 | 全部隐藏 | 拒绝（`activity_closed`，不扣任何东西） |

**实现要点**：
- 前端读取开关：应用启动时从服务端配置接口拉取（`GET /api/config` 或 `supabase.rpc('get_app_config')`），缓存并随配置变更刷新；开关关闭时前端直接隐藏全部入口，**不向后端发起任何邀请相关请求**。
- 后端强约束：发放 RPC 内部先查开关，关闭则返回 `activity_closed`——即使前端绕过/缓存了开启状态，也无法在关闭期间发放（服务端权威，防绕过）。
- 关闭不回收（R10）：已发放奖励（`referrals.status='granted'`）保持不变；`revoked` 仅由后台手动撤销触发。

**放置位置（后台）**：新增「系统设置」页面（或挂在用户管理页顶部设置区，见 §6.3 FR-16），侧边栏增加入口。

## 5. 业务流程

### 5.1 邀请人侧流程

```
[前置：活动总开关关闭时，本入口不显示（§4.3）]
已登录用户 → 个人中心「邀请好友」卡片
   ├─ 展示：专属邀请链接（可复制） / 6位邀请码（可复制）
   ├─ 展示：已邀请 N 人 · 已获得 X/2 次免费导出
   ├─ 点「复制链接」→ 复制 https://resume.xnkun.com/?ref=CODE
   └─ 点「复制邀请码」→ 复制 6 位码，可分享到任意渠道
```

### 5.2 新用户侧流程（链接带参）

```
[前置：活动总开关关闭时，注册表单不显示「邀请码」输入框，本流程整体不可用（§4.3）]
好友点击 https://resume.xnkun.com/?ref=CODE 进入
   ├─ 前端读取 URL 参数 ref，写入 localStorage（key: referral_code）
   │     ⚠️ 必须用 localStorage 而非 sessionStorage（微信 WebView 会清 sessionStorage）
   ├─ 用户点击注册 → AuthModal 打开
   ├─ 注册表单「邀请码」输入框自动预填 localStorage 中的码（可修改/清空）
   ├─ 邮箱密码注册成功
   │     ├─ Supabase 触发器 handle_new_user() 创建 users 默认记录
   │     ├─ 前端读取注册表单中的邀请码 + 设备指纹
   │     └─ 调用服务端 RPC grant_referral_reward() → 新用户 +1、邀请人 +1
   └─ 注册成功提示（若邀请关系建立成功，提示「你和好友各获得 1 次免费导出」）
```

### 5.3 新用户侧流程（手动填码）

```
[前置：活动总开关关闭时，注册表单不显示「邀请码」输入框（§4.3）]
新用户直接打开 App → 注册 → AuthModal 注册表单
   ├─ 「邀请码（选填）」手动输入 6 位码
   └─ 注册成功后同上调用 RPC 建立邀请关系
```

### 5.4 奖励发放时序（关键）

1. 用户**注册成功**（Supabase 返回 user）后，前端才发起奖励发放调用。
2. 若注册时 URL 带 `ref`，自动预填；用户可删除（删除则按手动码处理）。
3. 发放通过 RPC 完成，**不经过前端直接 UPDATE users 表**（服务端权威 + 原子 + 幂等）。
4. RPC 内部第一步校验活动开关：关闭 → 直接返回 `{ rewarded: false, reason: 'activity_closed' }`，不发放、不写流水（§4.3）。
5. 若发放请求失败（网络中断等），注册流程**不阻断**；用户下次打开应用时前端做一次幂等重试。

**交互设计**：

- **已登录用户**：CTA 改为「复制邀请链接」（进入个人中心邀请卡片或直接复制）。
- **数据来源**：板块所需开关状态与展示文案，与应用启动时的配置读取（§9.4）一并获取；开启才渲染。
- **落地页位置**：`LandingPage.tsx` 中「精选黄金模板展示」（`#landing-featured-templates`）之后、「行业深度定制场景」之前；如后续首页结构调整，以「活动板块跟随首页主视觉区」为原则。

### 6.5 边界情况

| 编号 | 场景 | 处理 |
|------|------|------|
| E-1 | 邀请码不存在 / 无效 | 不阻断注册；奖励不发放；给出「邀请码无效」提示 |
| E-2 | 邀请码是用户自己的 | 拒绝建立关系（R7），提示「不能邀请自己」 |
| E-3 | 同一邮箱重复注册 | Supabase 原生拒绝，无二次发放风险 |
| E-4 | 已被邀请过（重复绑定） | 幂等返回，不重复发放（R8） |
| E-5 | 邀请人已达 2 次上限 | 新用户仍 +1；邀请人不加（R4） |
| E-6 | 老用户无邀请码（历史数据） | 惰性生成（读个人中心/RPC 时若无码则补生成） |
| E-7 | 发放请求失败 | 注册不阻断；幂等重试机制兜底 |
| E-8 | 新用户通过链接进入但复制/修改了码 | 以注册表单最终提交的码为准 |
| E-9 | 匿名/未注册用户访问链接 | 存 localStorage 待注册后使用 |
| E-10 | 同设备反复注册马甲号 | 设备指纹拦截（§7） |
| E-11 | 用户带着 `?ref=CODE` 链接访问，但活动已关闭 | 注册表单不显示邀请码输入框；`ref` 参数忽略，不写入 localStorage；不发放（R9） |
| E-12 | 注册成功瞬间活动被关闭（开关切换竞态） | 以 RPC 内查询到的发放时刻开关状态为准；关闭则不发放，注册本身不受影响 |
| E-13 | 活动开启期间注册，事后活动关闭 | 已发放奖励保留（R10），不回收 |
| E-14 | 活动关闭期间注册，事后活动重新开启 | 不补发（R10）；用户可正常参与后续新邀请 |
| E-15 | 活动关闭时后端仍收到发放请求（前端缓存/绕过） | RPC 拒绝返回 `activity_closed`，不发放、不写流水（§4.3 后端强约束） |

## 7. 反作弊设计（最低防线）

> 鉴于 D1「注册即发」的高暴露面，下列防线为**必须项**（P0），上线后按 §10 监控持续加固。

| # | 防线 | 说明 | 优先级 |
|---|------|------|:---:|
| AC-1 | **邀请关系唯一** | `referrals.invitee_id` 唯一约束，一人只能归属一个邀请人 | P0 |
| AC-2 | **禁止自邀** | RPC 校验邀请码持有者 ≠ 调用者 | P0 |
| AC-3 | **设备指纹拦截** | 前端生成持久化 `device_id`（localStorage + 随机数），RPC 记录并标记 `device_suspect`；同设备再次绑定邀请关系时，新用户自己仍 +1，但**邀请人奖励不发**（防马甲号给同一邀请人重复刷奖励） | P0 |
| AC-4 | **发放幂等** | RPC 事务内唯一约束 + `ON CONFLICT DO NOTHING`，重试/并发不重复发放 | P0 |
| AC-5 | **服务端权威发放** | 奖励一律经 RPC（SECURITY DEFINER），前端不能直接改配额字段 | P0 |
| AC-6 | **审计流水** | `referrals` 表全量记录（邀请人、被邀请人、时间、device_id、状态），后台可查可撤销 | P0 |
| AC-7 | **IP 频控**（建议） | 服务端按 IP 限制注册/绑定频率，防同 IP 批量刷 | P1 |
| AC-8 | **管理员撤销** | 后台对异常奖励可回滚（扣回额度 + 标记 revoked） | P1 |

## 9. 数据模型设计

### 9.1 `users` 表新增字段

```sql
ALTER TABLE public.users
  ADD COLUMN IF NOT EXISTS invite_code TEXT UNIQUE;      -- 6 位邀请码，注册时生成
```

- 生成规则：6 位大写字母+数字，排除易混淆字符（0/O、1/I/L），校验唯一。
- 生成时机：`handle_new_user()` 触发器内生成；历史用户惰性补生成（RPC 或读取时）。

### 9.2 新增 `referrals` 表

```sql
CREATE TABLE IF NOT EXISTS public.referrals (
  id            BIGSERIAL PRIMARY KEY,
  inviter_id    UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  invitee_id    UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE UNIQUE,  -- AC-1
  invite_code   TEXT NOT NULL,
  device_id     TEXT,                                                               -- AC-3
  inviter_bonus INTEGER NOT NULL DEFAULT 0 CHECK (inviter_bonus IN (0, 1)),         -- 邀请人本次是否获奖励
  device_suspect BOOLEAN NOT NULL DEFAULT false,                                     -- 疑似同设备马甲（AC-3）
  status        TEXT NOT NULL DEFAULT 'granted' CHECK (status IN ('granted', 'revoked')),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  revoked_at    TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS idx_referrals_inviter ON public.referrals(inviter_id);
CREATE INDEX IF NOT EXISTS idx_referrals_invitee ON public.referrals(invitee_id);
```

- `invitee_id` 唯一 → 一人只能归属一个邀请人，天然幂等。
- `inviter_bonus` 区分「新用户奖励」与「邀请人奖励」的发放情况，便于撤销时精确回滚。

### 9.3 新增 RPC：`grant_referral_reward`

```
grant_referral_reward(p_invite_code TEXT, p_device_id TEXT)
  RETURNS JSONB
  SECURITY DEFINER SET search_path = public
```

事务内逻辑（服务端权威，原子）：

0. **第一步：查活动总开关（R9）** — 读取 `app_config` 中 `key='referral_activity'` 的 `value->>'enabled'`，为 `false` 直接返回 `{rewarded: false, reason: 'activity_closed'}`，不发放、不写流水。
1. `auth.uid()` 为调用者（新用户）；无会话拒绝。
2. 校验 `p_invite_code` 存在且持有者 ≠ 调用者（AC-2），无效返回 `{rewarded: false, reason: 'invalid_code'}`。
3. 校验调用者尚未在 `referrals` 有记录（`invitee_id` 唯一，R8）→ 已有则返回 `{rewarded: true, already: true}`（幂等）。
4. 校验 `p_device_id` 是否在 `referrals.device_id` 中出现过（AC-3）：
   - 未出现过 → 正常路径；
   - 已出现过（疑似同设备马甲）→ **不拦截新用户自己的 +1**，但邀请人奖励不发（`inviter_bonus = 0`，`status = 'granted'` 且追加 `device_suspect = true` 标记），仍写入 referrals 记录供后台核查。
5. 锁邀请人行（`SELECT ... FOR UPDATE`），统计 `inviter_bonus=1` 的已发次数：
   - 若 `< 2`（R3）：邀请人 `remaining_pdf_exports + 1`，`referrals.inviter_bonus = 1`；
   - 若 `≥ 2`（R4）：邀请人不再 +1，`referrals.inviter_bonus = 0`。
6. 新用户 `remaining_pdf_exports + 1`（R1/R5）。
7. 写入 `referrals` 一条记录（含 device_id）。
8. 返回 `{rewarded: true, inviterBonus, inviterQuotaReached}`。

### 9.4 调用链路（前端）

```
注册成功 → 读取邀请码(表单/localStorage) + device_id
        → supabase.rpc('grant_referral_reward', { p_invite_code, p_device_id })
        → 按返回结果更新 UI / 展示提示
```

> 前端入口显隐依据：应用启动/进入注册/个人中心/首页时拉取配置（`get_app_config` 或 `GET /api/config`），按 `referral_enabled` 决定各入口是否渲染；关闭时不发任何邀请相关请求。

### 9.5 新增配置表：`app_config`（活动总开关载体，D6）

```sql
CREATE TABLE IF NOT EXISTS public.app_config (
  key          TEXT PRIMARY KEY,
  value        JSONB NOT NULL DEFAULT '{}'::jsonb,
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_by   UUID REFERENCES auth.users(id)
);
INSERT INTO public.app_config (key, value)
VALUES ('referral_activity', '{"enabled": false}'::jsonb)
ON CONFLICT (key) DO NOTHING;
```

- 约定：开关默认 **`false`（关闭）**，即活动默认不生效；由管理员在后台开启。
- 访问控制：
  - **读**：`get_app_config()`（SECURITY DEFINER）对所有已认证/未认证用户开放（仅暴露开关布尔值，不暴露敏感配置）。
  - **写**：仅服务端（service_role）或 `set_app_config()`（SECURITY DEFINER + 校验 `is_admin`）可写。
- 后台「系统设置」页读写该 key（FR-16/FR-17）。

### 9.6 幂等与重试

- `referrals.invitee_id` 唯一约束 + RPC 内部检查 → 重复调用不重复发放。
- 前端在 App 启动时（已登录）做一次「未完成绑定则重试」的幂等补偿调用。

### 9.7 users 表 RLS 安全缺口修复（D10，随本功能一并做）

**现状缺口**（[20260603_commerce.sql](yiyejianli/supabase/migrations/20260603_commerce.sql) 当前策略）：

```sql
CREATE POLICY "Only server can update users"
  ON public.users FOR ALL USING (auth.uid() = id) WITH CHECK (auth.uid() = id);
```

- 该策略允许**已认证用户直接 UPDATE 自己行的任意字段**（含 `remaining_pdf_exports`、`tier`、`member_until`），即用户可自改配额/自封会员。

**修复方案**（新增迁移）：

```sql
-- 收紧：删除允许用户 UPDATE 自身行的策略（此策略是缺口根源）
DROP POLICY IF EXISTS "Only server can update users" ON public.users;

-- 保留用户只读自己数据（原 "Users can read own data" 已存在，无需重建）
-- 配额/权益变更一律走 RPC / 触发器（SECURITY DEFINER，绕过 RLS）
```

- **影响面评估**：需同步排查当前代码中所有直接 `updateUser()` 写 `users` 的调用点（如 [supabaseUserService.ts](yiyejianli/src/lib/supabaseUserService.ts) 的 `updateUser`、[App.tsx:604](yiyejianli/src/App.tsx#L604) 的扣配额），改为服务端 RPC（`consume_quota` / 支付回调 `complete_payment_order` 本就走服务端，不受影响）。
- 迁移需与前端改造同批发布，避免收紧后旧前端扣配额失败。

## 11. 非功能需求

| 项 | 要求 |
|----|------|
| **并发安全** | RPC 事务内行锁 + 唯一约束，并发注册不重复发放 |
| **幂等性** | 网络重试 / 重复调用不产生二次奖励 |
| **可审计** | referrals 全流水可追溯，后台可撤销 |
| **兼容性** | 微信内置浏览器（WebView）下链接带参、localStorage、复制剪贴板均可用 |
| **性能** | 邀请数据量小，无性能瓶颈；后台列表分页即可 |
| **可配置** | 活动启停零发版：后台开关即时生效（前端入口显隐 + 后端发放拒绝） |
| **安全** | RLS 收紧后普通用户无法直接写 users 表配额/权益字段（D10） |

## 12. 验收标准

| # | 场景 | 预期结果 |
|---|------|---------|
| T1 | A 邀请 B，B 注册成功 | B +1 次，A +1 次（A: 1/2） |

| T7 | 同一设备注册多个账号绑定同一邀请码 | 第 1 个生效，后续邀请人奖励被拦截（AC-3） |

| T11 | 后台撤销某条邀请奖励 | 该条标记 revoked，对应额度扣回，可二次确认 |
